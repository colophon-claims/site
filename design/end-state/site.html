A Colophon run

Have Colophon run it.

The same sealed method, run on a venue Colophon controls. The method is locked and anchored the same way. The numbers are computed the same way. The bundle is checked with the same free command, by the same seven checks.

What changes

Exactly three lines of the sealed disclosure change hands, from the claimant's word to Colophon's.

Self-run says the disclosure sealed into every self-run claim, verbatim Colophon-run says
"This is a local, self-run venue: the same operator controls task dispatch, execution, and evaluation." Colophon controlled task dispatch, execution and evaluation on a venue the claimant did not control.
"Pre-registration here is a discipline enforced by this tool, not a proof against the run's own owner. Nothing prevents the owner from having altered the record before publishing it." Unchanged
This line does not flip. The tool is still the thing enforcing pre-registration, and a reader still has to take the anchor rather than the operator's word.
"Run pinning on the harness, model, and loadout axes is enforced by an admission gate at dispatch time." Run pinning on the harness, model and loadout axes was enforced by Colophon's admission gate at dispatch time, on a venue whose isolation policy Colophon set and can state.
"Cost figures, where present, are self-reported by this venue and were never independently settled." Cost figures were recorded by Colophon on its own venue. They are not the claimant's report of them.

What does not change

The number lands where it lands. There is no badge, no score, and nothing on this page is for sale. Who paid is disclosed inside the bundle, before the run, not after the result is known.

What this is not

Not a certification. Not an endorsement. Not a widening of the evidence: the same seven checks run on the same bundle, and they still prove the math and not the honesty. A Colophon-run record answers one question that a self-run record cannot answer, and that is the only question it answers.

Seal a claim: bring your run

Six steps. You run the benchmark on the harness you already use; Colophon reads that run into a sealed record and publishes it, and a stranger checks the record without asking you for anything.

  1. Step 1

    Lock the method

    Fix what will be run, and what will count, before any result exists. The lock is timestamped by someone who is not you, and the commitment is pushed somewhere public.

    seal a claim
    $ npx @colophon-claims/cli method terminal-bench-2.1
  method     terminal-bench-2.1
  coverage   full
  tasks      89, fixed by the suite, not by you
  scorer     the suite's own scorer, pinned by digest
  suite      upstream commit mock-8c41f0a2

$ npx @colophon-claims/cli arm add --name "example-agent 0.3 (fictional)"
  arm 1 of 1   example-agent 0.3 (fictional)
  Supplied by the claimant. Colophon does not look inside it.

$ npx @colophon-claims/cli lock
  method digest   sha256:mock-7f3a91c4d0e28b56
  locked at       2026-09-04T10:12:00Z
  The method is fixed before any result exists.
  Nothing in the sealed freeze moves once the run starts.

$ npx @colophon-claims/cli anchor
  submitted to OpenTimestamps   ots:mock-pending
  calendar attestation          received
  Bitcoin attestation           follows in hours. Nothing waits on it.

$ npx @colophon-claims/cli freeze-repo export ./commitment
  wrote ./commitment    lock, anchor receipt, instrument digests
  Push this somewhere public. The anchor proves when. The commit proves what.

    What the anchor proves

    One thing. This exact method digest existed at this time, before any result existed. It does not prove the method is a good method, and it does not prove the claimant is honest. It removes one argument only, and it is the argument that gets made most: that the method was chosen after the number came back.

  2. Step 2

    Run the benchmark on your harness

    Colophon is not in this step. It does not dispatch the tasks, it does not host the container, and it does not watch. It reads what comes out, and the record says so.

    the claimant's own machine
    $ harbor run --dataset terminal-bench@2.1 --agent example-agent-0.3 --out ./jobs
  89 tasks dispatched
  89 tasks finished
  wrote ./jobs
  3. Step 3

    Bring it back

    The finished run is read against the slate you sealed in step 1. Every task has to be present once, every outcome has to come from the closed vocabulary, and every gap has to carry a stated reason. There is no flag that drops a row.

    bring the run back
    $ npx @colophon-claims/cli run import --from harbor ./jobs
  reading ./jobs against the sealed slate

  every task present once            89 of 89
  every outcome from the closed vocabulary
      pass                              61
      fail                              24
      timeout                            3
      error                              1
                                        89
  every gap counted with a stated reason
      task mock-0412: timeout, reason: container exceeded 30m
  exclude flag                       none offered, none accepted

  source dump digested and bound     sha256:mock-b20d47e9f1c85a03

$ npx @colophon-claims/cli collect
  89 rows, 4 outcome classes, 0 rows dropped

$ npx @colophon-claims/cli report
  report written. The self-run disclosure is sealed with it.
  4. Step 4

    Publish and host the bundle

    The bundle is the whole record: the evidence, the logs, the report and the timestamp proof, under one digest. Put it somewhere public and permanent. Its address is the thing you hand to a doubter.

    publish the bundle
    $ npx @colophon-claims/cli publish
  bundle    ./mock-bundle/
  digest    sha256:mock-3d9ac10e7b46f582
  format    benchmark-product-public-bundle/7
  A brought run carries the import marker as its own capability.
  5. Step 5

    Anyone checks it

    One command, free, forever. It recomputes the numbers from the evidence in the bundle and runs seven checks: manifest, evidence-closure, trust, matrix-rederivation, report-verification, claim-consistency, integrity-anchors.

    npx @colophon-claims/verify@0.2.1 ./mock-3d9ac10e7b46f582

    That is the same command a stranger runs on the bundle you published. Verification opens no network connection, reads no account or API credential, and uploads nothing. Find a claim.

  6. Step 6

    List it on its board

    Hand the site the bundle's address. The site runs the same published checker cold and lists what passes, next to every other claim sealed on the same method. No account, no email address.

What a seal proves and what it does not

A self-run report seals its own disclosure with it, and the disclosure is written to be read by someone who does not trust you. These are its first four lines, quoted from the disclosure sealed into every self-run claim:

  1. "This is a local, self-run venue: the same operator controls task dispatch, execution, and evaluation."
  2. "Pre-registration here is a discipline enforced by this tool, not a proof against the run's own owner. Nothing prevents the owner from having altered the record before publishing it."
  3. "Run pinning on the harness, model, and loadout axes is enforced by an admission gate at dispatch time."
  4. "Cost figures, where present, are self-reported by this venue and were never independently settled."

Item 2's second sentence is joined with a full stop here; the sealed record uses a dash. Item 3 is cut after "at dispatch time." Nothing else is changed.

Checking ends at the math, not at honesty. It confirms the record is closed, internally consistent, and unaltered since the anchor. It does not prove that the machine which produced the run was honest. A checked self-run bundle is still a self-run bundle, which is why the venue is written at the top of every claim page. If who ran it is the question you have to answer, Colophon can run it instead.
